# Natural-Key Globalization — Deferred Follow-ups

Context: as part of the `eaf_dev_natural_keys` work, we agreed to make natural
primary keys (visit_occurrence_id, visit_detail_id, provider_id, care_site_id,
location_id, episode_id, plus their self-FKs) globally unique by rewriting them
to `hash(CONCAT(value, site)) % 9223372036854775807`. That work happens in a
new endpoint (`/unique_natural_keys`) / Cloud Run job between
`filter_connect_participants` and `harmonize_vocab`.

The items below are explicitly **out of scope** for that change and are parked
here so we don't lose them.

---

## 1. Derived-table primary keys are not site-salted

Tables: `observation_period`, `condition_era`, `drug_era`, `dose_era`.

These are generated by `generate_derived_data_from_harmonized` in
`core/omop_client.py` using the SQL in `reference/sql/derived_tables/`. Their
primary keys (`observation_period_id`, `condition_era_id`, etc.) are produced
by the derived-table SQL without any site salt, so they can collide across
sites just like the natural keys we're fixing.

These tables are listed in `constants.SURROGATE_KEY_TABLES`, but unlike the
clinical surrogate-key tables they do **not** go through
`transformer.omop_to_omop_etl`, which is where the site-salted re-hash lives.
So the existing "surrogate keys are globally unique" claim does not hold for
derived tables.

Plausible fix: rewrite the derived-table PK columns in
`generate_derived_data_from_harmonized` (or in a post-processing pass) using
the same `hash(row_values + site)` pattern the transformer uses.

## 2. Polymorphic event-ID foreign keys

These columns reference different target tables depending on the value of a
sibling `*_event_field_concept_id` column:

- `measurement.measurement_event_id` (gated by `meas_event_field_concept_id`)
- `observation.observation_event_id` (gated by `obs_event_field_concept_id`)
- `note.note_event_id` (gated by `note_event_field_concept_id`)
- `cost.cost_event_id` (gated by `cost_event_field_concept_id`)
- `episode_event.event_id` (gated by `episode_event_field_concept_id`)

The natural-key rewrite can't blindly hash these — the correct transformation
depends on which table the row points at on a per-row basis. Some pointer
targets are surrogate-key tables (already site-salted), some are natural-key
tables (will be site-salted after this work), and some may be `person`
(must not be touched).

Needs a per-event-field-concept-id case statement, plus a way to enumerate the
valid target tables. Defer until after the main natural-key work lands.

## 3. `note_nlp.note_id` referential-integrity break (pre-existing)

`note_nlp.note_id` is a FK to `note.note_id`. `note` is in
`VOCAB_HARMONIZED_TABLES`, so its `note_id` is rewritten by
`transformer.omop_to_omop_etl` to `hash(row_values + site)`. But `note_nlp` is
**not** in `VOCAB_HARMONIZED_TABLES` — it stays in `converted_files/` and
never gets the same rehash applied to its `note_id` column. So in the current
pipeline, `note_nlp.note_id` values no longer match the rehashed
`note.note_id` they were originally pointing to.

This is independent of the natural-key work — it's a bug in how the surrogate
rehash interacts with `note_nlp`. Fix likely belongs in either the transformer
flow (route `note_nlp` through a parallel rewrite) or a small dedicated pass
that mirrors `note`'s PK transformation into `note_nlp.note_id`.

## 4. DAG wiring (Airflow, not this repo)

This repo exposes the endpoint + Cloud Run job. The Airflow DAG that
orchestrates the pipeline lives elsewhere and must be updated to:

- Schedule it after `filter_connect_participants` and before `harmonize_vocab`.
- Pass `site` (already known to the DAG), `file_path`, and `omop_version`.

Track separately from this repo's PR.
