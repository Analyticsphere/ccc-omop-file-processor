GUIDING PRINCIPLES (from your brief)
--------------------------------------------------------------------------------
1. The file processor is largely AGNOSTIC about whether a version is a "target".
   It just operates on whatever CDM/vocab version is handed to it. Therefore,
   only rename a function/class/var to `target_*` when the code is *truly* about
   the target (i.e., the value is the version the data is being upgraded *to*,
   loaded *into* cdm_source as the final version, or recorded in the report as
   the standardization target).

2. After determining target-vs-agnostic, switch terminology:
       omop_version          → cdm_version
       target_omop_version   → target_cdm_version
       vocab_version         → vocab_version       (NO RENAME — already correct)
       target_vocab_version  → target_vocab_version (NO RENAME — already correct)

   Note: the user listed `vocab_version`/`target_vocab_version` in the targets,
   but those names already use the right vocabulary. The "omop" → "cdm" swap
   only affects the CDM-version names. I'll flag this in the discussion section
   for confirmation.

3. The naming inside the codebase is already partially inconsistent — many
   modules already use `cdm_version` internally (normalization, transformer,
   utils, vocab_harmonization, pipeline_log, reporting, transformer). This
   refactor brings the remaining laggards in line.

PHASES
================================================================================
This refactor crosses the API boundary, so the contract between the orchestrator
and the file processor MUST be updated in lock-step. The plan below walks
through it in a sequence that avoids a broken state in production.

The endpoint JSON payload keys and Cloud Run job env-var names ARE the contract;
internal Python parameter names are not. We can change internal names freely;
crossing-the-wire names need coordination.

There are three "wire" surfaces:
    (a) HTTP endpoint JSON body keys (e.g., `omop_version` in POST bodies)
    (b) Cloud Run job environment variable names (e.g., `OMOP_VERSION`,
        `TARGET_OMOP_VERSION`)
    (c) The `cdm_source_data` dict that the DAG hands to the populate endpoint
        verbatim (keys `target_omop_version` + `target_vocab_version`)
